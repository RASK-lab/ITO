# くつしたのデータ

ITO が返す「くつした」は、あらかじめ作った 50 種で固定です。その画像と台帳（名前、説明、分類）の置き場所、名前の決まり、項目の意味、直し方をまとめています。

## 置き場所

元データ（正）は `data/socks/` に置き、アプリが使う分は、そこから作った「写し」を置いています。

| 場所 | 中身 | 区別 |
|---|---|---|
| `data/socks/socks.json` | くつしたの台帳。人が編集するのはここだけ | 正 |
| `data/socks/original/worn-01.png` … | 元の画像（PNG）。50 枚 | 正 |
| `front/public/socks/worn-01.webp` … | 表示用の画像（WebP）。50 枚 | 写し |
| `back/src/resources/socks.json` | バックエンド用の台帳 | 写し |
| `front/public/share/worn-01.jpg` … | シェア用のカード画像（1200 × 630）。50 枚 | 写し |
| `front/public/s/worn-01/index.html` … | シェア用のページ。カード画像の指定（OGP）を書いたもの。50 個 | 写し |
| `scripts/build-socks.sh` | 正から写しを作り直すコマンド | — |

- 写しは手で編集しない。直すときは `data/socks/` を編集して、`scripts/build-socks.sh` を実行する。
- 正と写しを分けているのは、フロントのコンテナには `front/` だけ、バックエンドのコンテナには `back/src/` だけが入り、リポジトリ直下の `data/` はどちらからも直接読めないため。
- くつしたは増えない固定のものなので、データベースにもオブジェクト置き場にも入れず、Git で管理する。
- [data.md](data.md) の「くつした」の節は、見本 3 種だったときの内容です。くつしたについては、この文書が新しい内容です。

## 名前の決まり

- くつしたの ID は `系統-番号` の形（例: `WORN-01`）。系統は大文字、番号は 2 桁。分析が返す値や、記録に残す値にはこの ID を使う。
- ファイル名は、ID を小文字にしたもの。ID が決まれば、ファイルの場所はすべて決まる。

| ID | 元の画像 | 表示用の画像 | 画面から見える URL |
|---|---|---|---|
| `WORN-01` | `data/socks/original/worn-01.png` | `front/public/socks/worn-01.webp` | `/socks/worn-01.webp` |

ファイル名を小文字にしているのは、URL として扱いやすくするためと、大文字と小文字を区別する環境としない環境で動きが変わらないようにするためです。

## 画像の決まり

画像は 2 種類あります。

| | 元の画像 | 表示用の画像 |
|---|---|---|
| 場所 | `data/socks/original/` | `front/public/socks/` |
| 形式 | PNG（劣化なし） | WebP（軽い） |
| 大きさ | 512 × 512 ピクセル、背景は透明 | 同じ |
| 1 枚の重さ | 168〜309KB（合計 11.6MB） | 27〜60KB、平均 40KB（合計 2.0MB） |
| 使うところ | 深層学習の学習。表示用の画像を作る元 | 画面 |
| 配り方 | 配らない（ブラウザからは見えない） | 静的ファイルとしてフロントと一緒に配る |

- 元の画像は加工しない（大きさを変えない、圧縮し直さない）。用意されたファイルをそのまま置く。
- 学習には元の画像を使う。表示用の画像は圧縮で色がわずかに変わっているため、学習には使わない。
- 表示用の画像は、元の画像から次の設定で作る。透明の部分（アルファ）は元とまったく同じになる。

```bash
cwebp -q 85 -alpha_q 100 -m 6 worn-01.png -o worn-01.webp
```

- 画面では、表示する分だけが読み込まれる。50 枚あっても、最初にまとめて読み込まれることはない。

## 写しを作り直す

```bash
scripts/build-socks.sh
```

リポジトリのどこから実行しても動きます。`cwebp` が必要です（`brew install webp`）。1 分ほどかかります。

やること:

1. `data/socks/original/*.png` をすべて WebP に変換して、`front/public/socks/` に置く。
2. `socks.json` の ID と PNG、`image` と WebP が過不足なくそろっているかを照合する。足りないもの・余っているものがあれば、名前を出して失敗で終わる。
3. `data/socks/socks.json` を `back/src/resources/socks.json` にコピーする。
4. シェア用のカード画像とページを作り直す（`scripts/build-share.py`。これだけを実行してもよい）。Pillow（`pip install pillow`）と日本語のフォントが必要。

### シェア用のカード画像とページ

X などに投稿されたアドレスの下に、画像つきのカードを出すためのものです。投稿されると、X がそのページを読みに来て、書いてあるカード画像を出します。人がページを開くと、最初の画面に移ります。

結果の画面の「シェア」での使われ方:

- X: ふつうは、結果ごとのページ（`/api/share/<記録の ID>`。カードに、書いた「と」も入る。[api.md の「シェア」](api.md#シェア結果ごとのカード)）を投稿の文に入れる。結果ごとのページをまだ用意できていないときと、用意できなかったときだけ、ここで作るくつしたごとのページ（`/s/worn-01/`）を入れる。
- LINE: いつも、くつしたごとのページを入れる。

- カード画像は X が外から取りに来るので、ページには本番のドメインから始まるアドレスを書く。いまは `https://hackathon-ito-app.team-kutsushita.workers.dev` を書いている。**本番のドメインが変わったら、`scripts/build-share.py` の `SITE_URL` を直して作り直す**（ページのアドレスが本番と違うと、カードに画像が出ない）。
- カードが出るかどうかは、本番に公開してからでないと確かめられない。
- カード画像はくつしたごとに 1 枚で、書いた人の名前や、書いた「と」は入らない（書いた「と」が入るのは、結果ごとのページのカード）。

注意:

- 表示用の画像は、起動中の画面にそのまま反映される（コンテナを作り直さなくてよい）。
- 余っている WebP は自動では消さない。名前が出たら、手で消してからもう一度実行する。
- `cwebp` の版が違うと、同じ PNG からでも中身が少し違う WebP ができることがある。直していないくつしたの WebP が差分に出たら、その分はコミットに入れない。

## 台帳（`socks.json`）の形

```json
{
  "imageWidth": 512,
  "imageHeight": 512,
  "format": "WebP",
  "items": [
    {
      "id": "WORN-01",
      "level": 1,
      "rarity": "使い古し",
      "name": "穴あき灰色",
      "comment": "灰色のウール靴下はかかとに大きな穴が開き、縁から糸が垂れている。",
      "image": "/socks/worn-01.webp",
      "classification": {
        "feature": "雑",
        "beauty": 1,
        "review": {
          "fit": "合う",
          "reason": "大きな穴と垂れた糸で輪郭が大きく崩れている。"
        }
      }
    }
  ],
  "classification": {
    "features": ["個性的", "雑", "…"],
    "beautyLevels": { "1": "かなり粗い", "…": "…" },
    "selection": "…",
    "assignmentRule": "…"
  }
}
```

書き方の決まり: インデントは半角スペース 2 つ、日本語はそのまま書く（`\u` の形にしない）、キーの順番は上の例のとおり、ファイルの最後は改行で終える。

### 最上位の項目

| 項目 | 内容 |
|---|---|
| `imageWidth`, `imageHeight` | 画像の大きさ（ピクセル）。元の画像も表示用の画像も同じ |
| `format` | `image` が指す表示用の画像の形式 |
| `items` | くつしたの一覧。50 件。系統ごとに、番号の順に並べる |
| `classification` | 分類の定義と、選び方の説明（下の「分類のしくみ」） |

### `items` の 1 件

| 項目 | 内容 |
|---|---|
| `id` | くつしたの ID。重複しない |
| `level` | 珍しさの段階。1〜6 の整数。系統ごとに決まっている |
| `rarity` | `level` を言葉で表したもの。系統ごとに決まっている |
| `name` | くつしたの名前 |
| `comment` | 絵の説明。1 文 |
| `image` | 表示用の画像のパス。`front/public/` から見た場所で、画面からはこのまま URL として使える |
| `classification.feature` | このくつしたが受け持つ「字の印象」。10 種のうちの 1 つ |
| `classification.beauty` | このくつしたが受け持つ「字の綺麗さ」。1〜5 の整数 |
| `classification.review.fit` | `feature` が絵に合っているかを見直した結果。いまは 50 件すべて「合う」 |
| `classification.review.reason` | そう判断した理由。1 文 |

推測で書いた部分:

- `level` は、数が大きいほど珍しいと読み取りました（`rarity` の言葉の並びから）。
- `review` は、データを作ったときの見直しの記録と読み取りました。画面に出す文かどうかは、元データからは分かりません。
- `comment` を画面に出すのか、分析の材料にするだけなのかも、元データからは分かりません。

## 系統と件数

ID の前半が系統です。系統と `level` と `rarity` は、1 対 1 で対応しています。

| 系統 | `level` | `rarity` | 件数 | ID |
|---|---|---|---|---|
| `WORN` | 1 | 使い古し | 9 | `WORN-01`〜`WORN-09` |
| `DAILY` | 2 | 素朴 | 9 | `DAILY-01`〜`DAILY-09` |
| `CRAFT` | 3 | 細工 | 9 | `CRAFT-01`〜`CRAFT-09` |
| `REGAL` | 4 | 上質 | 9 | `REGAL-01`〜`REGAL-09` |
| `HEIR` | 5 | 希少 | 9 | `HEIR-01`〜`HEIR-09` |
| `APEX` | 6 | 激レア | 5 | `APEX-01`〜`APEX-05` |
| 合計 | | | 50 | |

`REGAL` が 4、`HEIR` が 5 です（順番を間違えやすい）。

## 分類のしくみ

書かれた「と」を 2 つの値で表し、その組み合わせでくつしたを 1 つ決めるしくみです。

| 項目 | 内容 |
|---|---|
| `classification.features` | 字の印象の種類。10 種: 個性的、雑、可愛い、丁寧、かっこいい、繊細、達筆、不器用、暖かい、冷たい |
| `classification.beautyLevels` | 字の綺麗さの段階。1: かなり粗い、2: やや粗い、3: 標準、4: 整っている、5: とても整っている |
| `classification.selection` | 選び方を文章で書いたもの |
| `classification.assignmentRule` | どの系統のくつしたをどの組み合わせに割り当てたかを、文章で書いたもの |

- 選び方（`selection`）: 「と」の印象に最も近い `feature` を 1 つ選び、字の綺麗さ（`beauty`）を 1〜5 で評価する。両方が一致するくつしたを選ぶ。
- 印象 10 種 × 綺麗さ 5 段階 = 50 通りで、どの組み合わせにも、くつしたがちょうど 1 つある。
- `beauty` は「字」の綺麗さで、くつしたの出来ばえではない。たとえば `WORN-03` は印象が「丁寧」、綺麗さが 1 のくつした。
- `beautyLevels` のキーは文字（`"1"`）、各くつしたの `beauty` は数（`1`）。JSON ではキーに数を使えないため。
- `selection` と `assignmentRule` は人が読むための文章で、プログラムが読む決まった形ではない。

割り当ての表（`feature` と `beauty` から決まる ID）:

| `feature` | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 個性的 | WORN-02 | DAILY-08 | HEIR-02 | APEX-04 | HEIR-05 |
| 雑 | WORN-01 | WORN-05 | CRAFT-08 | CRAFT-09 | CRAFT-05 |
| 可愛い | WORN-09 | DAILY-03 | CRAFT-07 | REGAL-06 | REGAL-07 |
| 丁寧 | WORN-03 | DAILY-05 | REGAL-04 | REGAL-03 | HEIR-07 |
| かっこいい | DAILY-04 | DAILY-06 | REGAL-05 | REGAL-01 | REGAL-02 |
| 繊細 | WORN-07 | DAILY-07 | HEIR-08 | HEIR-04 | HEIR-01 |
| 達筆 | CRAFT-01 | CRAFT-02 | HEIR-06 | HEIR-09 | APEX-05 |
| 不器用 | WORN-08 | WORN-04 | CRAFT-06 | CRAFT-04 | CRAFT-03 |
| 暖かい | DAILY-02 | DAILY-01 | APEX-03 | REGAL-08 | APEX-02 |
| 冷たい | WORN-06 | DAILY-09 | HEIR-03 | REGAL-09 | APEX-01 |

割り当ての決まり（`assignmentRule`）と、実際のデータ:

- 綺麗さ 1・2 の 20 個は、`level` 1・2 の 18 件と、`level` 3 の 2 件（`CRAFT-01`、`CRAFT-02`）。
- `level` 4〜6 の 23 件は、すべて綺麗さ 3〜5。
- 印象が「雑」「不器用」のときは、綺麗さ 1・2 が `level` 1、綺麗さ 3〜5 が `level` 3。
- つまり、字が綺麗なほど珍しいくつしたになりやすい。ただし「雑」「不器用」は、どれだけ綺麗でも `level` 3 まで。

`assignmentRule` の文中の「レアリティ 1〜6」は、`level` の数のことと読み取りました（推測。数が実際のデータと合う）。

## くつしたを足す・差し替える

どの場合も、`data/socks/` を直してからコマンドを実行し、元データと写しを同じコミットに入れます。

絵を差し替える（ID はそのまま）:

1. 新しい PNG（512 × 512、背景は透明）を、同じ名前で `data/socks/original/` に置く。
2. 絵が変わって説明が合わなくなったら、`data/socks/socks.json` の `comment` と `review.reason` を直す。
3. `scripts/build-socks.sh` を実行する。
4. 画面で `http://localhost:5173/socks/<名前>.webp` を開いて確かめる。開いたままの画面は、古い画像を覚えていることがあるので読み込み直す。

名前や説明を直す:

1. `data/socks/socks.json` を直す。
2. `scripts/build-socks.sh` を実行する。

足す:

1. ID を決める（系統の中で次の番号。例: `APEX-06`）。
2. PNG を、ID を小文字にした名前で `data/socks/original/` に置く（例: `apex-06.png`）。
3. `data/socks/socks.json` の `items` に 1 件足す。`level` と `rarity` は系統の表に合わせ、`image` は `/socks/apex-06.webp` の形にする。
4. `scripts/build-socks.sh` を実行する。
5. この文書の件数の表と割り当ての表を直す。

足す・減らす・`feature` や `beauty` を変えるときの注意:

- いまは 50 通りの組み合わせに 1 つずつ割り当ててある。足すと同じ組み合わせにくつしたが 2 つでき、減らすと空きができる。分析の担当者と相談してから行う。
- `id` は、分析の結果や記録に残る値なので、一度使ったものは変えない・使い回さない。
- 減らすときは、`socks.json` の 1 件と PNG を消し、`front/public/socks/` の WebP も手で消してから、コマンドを実行する。

## 点検で見つかった気になる点

2026-11-28 に、元データを置いたときに調べた結果です。件数、ID の重複・欠番、画像との対応、系統と `level` と `rarity` の対応、分類の定義と各くつしたの値、割り当ての決まりには、食い違いはありませんでした。次の点は、直さずにそのままにしてあります。

台帳:

- `review.reason` が `comment` とまったく同じ文になっているものが 14 件ある（`WORN-03`、`WORN-04`、`WORN-07`、`WORN-09`、`CRAFT-01`〜`CRAFT-06`、`CRAFT-08`、`CRAFT-09`、`HEIR-06`、`APEX-05`）。理由ではなく、絵の説明になっている。
- `review.fit` は 50 件すべて「合う」で、値として区別がない。
- `assignmentRule` の「レアリティ」は `level`（数）を指していて、項目の `rarity`（言葉）とは別のもの。まぎらわしい。
- 文の終わり方がそろっていない。`comment` は `DAILY-07` だけ「…短い靴下。」と名詞で終わる。`review.reason` は「…ケーブル編み。」のように名詞で終わるものが 11 件、ほかは「…ている。」などの文。句点（。）はすべてに付いている。
- 表記のゆれ: 「短靴下」と「短い靴下」、「靴下」と「ハイソックス」「ロングソックス」。アプリの名前では「くつした」とひらがなだが、台帳の文はすべて「靴下」。
- 名前が似ているもの: 「パン屋の朝」（`DAILY-01`）と「郵便屋の朝」（`DAILY-05`）、「雪の降る聖夜」（`REGAL-09`）と「永遠の聖夜」（`APEX-02`）。同じ名前のものはない。

説明と絵:

- `WORN-07`: 名前は「霧色」、説明は「淡いからし色」。絵は黄色で、傷みや汚れがなく、「使い古し」には見えない。
- `HEIR-03`: 説明は「新月から満月まで順に並んでいる」。絵は、三日月から満月になり、また三日月に戻る並び。
- `DAILY-05`: 説明は「履き口に赤い切手の刺繍」。絵では、切手は履き口の折り返しより下にある。
- `DAILY-03`: 名前と説明は「水玉」。絵の模様は丸ではなく、小さな花（十字）の形。
- `DAILY-07`: `review.reason` は「透かし模様」を理由にしているが、`comment` には透かし模様のことが書かれていない。
- `HEIR-09`: 印象は「達筆」だが、絵は砂時計と飾りの曲線。ほかの「達筆」4 件（筆で引いたような線）とは絵の性格が違う。

画像:

- 50 枚すべてで、背景に消し残しのような、ごく薄い色が残っている（不透明度が平均 1〜4% ほどの薄い画素が、画像全体の 1〜15% を占める）。多いのは `WORN-05`、`WORN-08`、`WORN-06`、`REGAL-06`、`REGAL-07`。白や明るい背景ではほぼ見えない。濃い色の背景に置いたときや、影を付けたときに、うっすら見えるかもしれない。「透明でない部分」を機械的に切り出すと、くつしたの形ではなく四角に近い範囲になる（学習で使うときも注意）。
- くつしたの本体も、完全な不透明ではない（不透明度 98〜99%）。見た目には分からない。
- 絵が端で切れているもの、端に触れているものはない。ただし、まわりの余白はそろっていない（左右 39〜117 ピクセル、上下 38〜72 ピクセル）。丈の長いくつしたは細く、短いくつしたは横に広く写っているので、並べると見かけの大きさが違う。
- 表示用の画像は、拡大して比べると、紺地に金の細い線（`REGAL-01` など）の色がわずかに薄い。ふつうの大きさでは分からない。
