# Git 運用ルール

このリポジトリで使うブランチ名とコミットメッセージの命名規則です。

---

## 1. ブランチ名

### 形式

```
ナンバリング-f_ブランチ元-名前-詳細
```

| 部分 | 意味 | 例 |
|------|------|-----|
| ナンバリング | 3 桁の連番（001, 002, …）。新規ブランチごとに +1 | `001` |
| `f_` | feature（作業ブランチであることを示す接頭辞） | `f_` |
| ブランチ元 | このブランチを切った元のブランチ名 | `main` |
| 名前 | 作業者の名前（ローマ字・苗字など） | `kotani` |
| 詳細 | 作業内容。コミットタグと同じ語を使う | `feat_frontend` |

### 例

```
001-f_main-otoha-feat_frontend
002-f_main-satonico-fix_login
```

- 番号は既存ブランチの最大値 + 1 を使う。

---

## 2. コミットメッセージ

### 形式

```
タグ(スコープ): 変更内容の要約
```

- タグは下表から 1 つ選ぶ。
- 要約は日本語でよい。「何をしたか」を短く書く。
- 原因や測定結果がある場合は、末尾に括弧で添える。

例:

```
feat: 学習機能の追加
fix: OpenCV の内部スレッドを切る
docs: CLAUDE.md に「進め方の規律」を追加
```

### タグ一覧

| タグ | 使う場面 | 例 |
|------|----------|-----|
| `feat` | 新しい機能や処理を追加する |
| `fix` | 不具合を直す（原因や測定結果を括弧で添えると良い） | 
| `docs` | README・CLAUDE.md など文書だけの変更 | 
| `chore` | 設定値の変更、マシン追加、整理など、機能追加でも不具合修正でもないもの | 
| `perf` | 速度・メモリの改善（性能目的であることが明確なとき） | 
| `refactor` | 動作を変えずに、コードの置き場所や構造を変える | 
| `merge` | 別ブランチを取り込んだとき |
| `other` | 上のどれにも当てはまらないとき |

### 迷ったときの判断

- 機能が増えた → `feat`
- 直した → `fix`
- 文書だけ → `docs`
- 設定値・整理 → `chore`
- 動きは同じで構造だけ変えた → `refactor`
- 速くした／軽くした（目的が明確） → `perf`

---

## 3. 運用メモ

- ブランチ名・コミットメッセージは、レビューや `git log` で追いやすくするためのルール。
- 1 コミットには 1 つの目的だけを入れる。
- 既存の履歴は変更しない（ルール導入後の作業から適用する）。
