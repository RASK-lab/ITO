# データの形と置き場所

何を、どこに、どんな形で置くかの取り決めです。インフラと分析の担当と相談して変えていきます。

## 全体

| データ | 置き場所（本番の予定） | 手元での代わり | 形 |
|---|---|---|---|
| くつしたの元データ（50 種。台帳と元の画像） | Git で管理する（アプリからは直接読まない） | 同じ | `data/socks/socks.json`、`data/socks/original/worn-01.png` |
| くつしたの表示用の画像（元データから作る写し） | フロントと一緒に配る静的ファイル | 同じ | `front/public/socks/worn-01.webp` |
| くつしたのバックエンド用の台帳（元データから作る写し） | バックエンドの JSON ファイル | 同じ | `back/src/resources/socks.json` |
| 書かれた「と」の画像（大小 2 枚） | オブジェクト置き場（Cloudflare R2） | フォルダ `back/data/objects/` | キー `drawings/<id>_1024.png`、`drawings/<id>_256.png` |
| 書かれた「と」の線のデータ | オブジェクト置き場（Cloudflare R2） | フォルダ `back/data/objects/` | キー `drawings/<id>.json.gz` |
| 「と」の台帳（いつ、どの画像、分析結果） | データベース（Cloudflare D1） | SQLite のファイル `back/data/ito.sqlite3` | 表 `drawings` |
| 学習データの「と」（指示、申告、線のデータ） | データベース（Cloudflare D1） | 同じ SQLite のファイル | 表 `collect_samples`（[collect.md](collect.md)） |
| 学習データの「と」の画像 | オブジェクト置き場（Cloudflare R2） | フォルダ `back/data/objects/` | キー `collect/<id>_1024.png`、`collect/<id>_256.png` |

考え方:

- 画像のような大きいファイルは、データベースに入れない。オブジェクト置き場に入れ、データベースにはその名前（キー）だけを書く。
- くつしたは増えない固定のものなので、データベースにもオブジェクト置き場にも入れず、コードと一緒に Git で管理する。
- 手元の代わり（フォルダと SQLite）は、本番と同じキー・同じ表の形にしてある。差し替える場所は `back/src/storage.py`（オブジェクトを置く・消す）と `back/src/db.py`（台帳に書く）の 2 つだけ。`back/src/drawings.py` は、この 2 つを呼ぶだけで、ファイルの場所や SQL を知らない。
- 本番の置き場（R2 と D1）には、まだつないでいない。

Docker では `back/data/` はコンテナ内の `/app/data/` で、いまの `compose.yaml` では PC 側とつないでいないため、コンテナを作り直すと消えます。場所は環境変数 `ITO_DATA_DIR` で変えられます。

## くつした

くわしい説明（名前の決まり、画像の決まり、台帳の項目、直し方）は [socks.md](socks.md) にあります。ここには要点だけを載せます。

- くつしたは 50 種で確定している。ID は `WORN-01` のような「系統-番号」の形。
- 元データ（正）は `data/socks/`。台帳が `socks.json`、元の画像（PNG）が `original/`。人が編集するのはここだけ。
- `front/public/socks/`（表示用の WebP）と `back/src/resources/socks.json`（バックエンド用の台帳）は、元データから作る写し。手で編集しない。
- 写しは `scripts/build-socks.sh` で作り直す。

## 書かれた「と」

「確定」を押すと、バックエンド（`POST /api/drawings`）が 1 回の確定につき、オブジェクトを 3 つ置き、台帳に 1 行書きます。`<id>` は記録の ID（英数字 32 文字）です。

### オブジェクト（画像と線）

| キー | 中身 | 使いみち |
|---|---|---|
| `drawings/<id>_1024.png` | 1024 × 1024 ピクセルの画像 | 保存用。あとで画面に表示する |
| `drawings/<id>_256.png` | 256 × 256 ピクセルの画像 | 深層学習に渡す。一覧で小さく表示する |
| `drawings/<id>.json.gz` | 線のデータ。JSON を gzip で圧縮したもの（下の「線のデータ」） | 書き順や速さを使う分析。描き直し |

画像の決まり:

- 形式は PNG。白黒 1 チャネル（8 ビットのグレースケール。Pillow でいうモード `L`）。透明の情報は持たない。
- 白地（255）に黒い線（0）。線の縁には中間の濃さが残る（2 値化していない）。
- 枠の全体がそのまま入っている。書いた位置や大きさは変えていない（余白を切ったり、中央に寄せたりしていない）。
- 線の太さは一辺の 2% を中心に、筆圧（マウスと指は書く速さ）で 0.4〜1.6 倍に変わる（1024 で約 8〜33 ピクセル）。
- フロントが送る画像は、一辺が 1024 以上の正方形（[api.md](api.md) の「送る画像の大きさ」）。バックエンドは、それを白黒 1 チャネルにしてから、1024 と 256 のそれぞれに直接縮小する（方式は `BICUBIC`）。ちょうど 1024 で届いた画像は、縮小せずにそのまま 1024 の画像になる。
- 元の画素数と、書いた端末の画素密度は残さない（元の大きさには戻さない）。
- 1 枚あたりの大きさは、ふつうの「と」で、1024 が 8〜15KB、256 が約 3KB。細かく書き込むと大きくなる（短い線 2000 本で、1024 が約 140KB、256 が約 24KB）。

### 線のデータ

分析側の資料（「フロントから毎回届くもの」）の形のまま読めるよう、次の 3 項目だけを入れた JSON です。項目の意味は [api.md](api.md) の「送る内容」と「点」にあります。

```json
{
  "target": "と",
  "canvas": { "width": 1024, "height": 1024 },
  "strokes": [
    { "pointerType": "mouse", "points": [[409.6, 184.3, 0, 0.5], [414.1, 201.9, 21, 0.5]] }
  ]
}
```

- `target`: 書いた字。いまは `"と"` だけ。
- `canvas`: 座標の基準にした枠の大きさ。常に 1024 × 1024（保存する大きいほうの画像と同じ基準なので、座標はそのまま `_1024.png` の上の位置になる）。
- `strokes`: 線ごとの `pointerType`（`mouse`・`touch`・`pen`）と、点 `[x, y, t, pressure]` の並び。`x`・`y` は -1024〜2048（枠の中は 0〜1024）、`t` は最初の線を書きはじめてからの経過ミリ秒（整数）、`pressure` は 0〜1。
- 送られてきた内容のうち、この 3 項目だけを保存する（`image` や、決まっていない `intent` などは入れない）。値は変えない。ただし数の書き方は変わることがある（送られた `412` が `412.0` になる。値は同じ）。
- 圧縮は gzip（Python の標準ライブラリ。強さは 6）。展開すれば、元の JSON にそのまま戻る。

```python
import gzip, json
data = json.loads(gzip.decompress(open("<id>.json.gz", "rb").read()))
```

大きさの目安:

| 場合 | 圧縮前の JSON | 圧縮後 |
|---|---|---|
| ふつうの「と」（2 本、約 60 点） | 約 1.5KB | 約 0.65KB |
| 上限いっぱいの 20 万点（1 本の長い線） | 約 5MB | 約 0.5〜1.6MB（同じ位置の点ばかりで約 0.5MB、ばらばらの位置の点で約 1.6MB） |
| 上限いっぱいの 20 万点（点が 1 個だけの線ばかり） | 約 12MB | 約 0.5MB（同じ位置の点ばかりのとき） |

線のデータをデータベースに入れないのは、塗りつぶすように書くと大きくなるためです。データベース（D1）には 1 行の大きさに上限があります。

### 台帳（表 `drawings`）

| 列 | 型 | 内容 |
|---|---|---|
| `id` | 文字 | 記録の ID |
| `created_at` | 文字 | 記録した日時（UTC、ISO 8601。例 `2026-11-28T03:23:47+00:00`） |
| `image_1024_key` | 文字 | 1024 × 1024 の画像のキー |
| `image_256_key` | 文字 | 256 × 256 の画像のキー |
| `strokes_key` | 文字 | 線のデータのキー |
| `target` | 文字 | 書いた字。いまは `と` だけ |
| `duration_ms` | 整数 | 書くのにかかった時間（ミリ秒）。最初の線を書きはじめてから、最後の線を離すまで。バックエンドが、最後の線の最後の点の `t` を入れる |
| `stroke_count` | 整数 | 線の本数。バックエンドが数える |
| `point_count` | 整数 | 点の合計。バックエンドが数える |
| `sock_id` | 文字 | 結果のくつしたの ID（例 `WORN-01`）。いまは仮の結果（50 種から無作為に選んだもの）が入る。分析ができたら、分析で選んだくつしたが入る |
| `font` | 文字 | 似ているフォント。分析前は空 |
| `reading` | 文字 | 「と」についての読み解き。分析前は空 |
| `message` | 文字 | くつしたと絡めたメッセージ。いまは仮の結果（決まった文に、くつしたの名前を入れた一行）が入る |
| `user_name` | 文字 | 書いた人のユーザーネーム。確定のときに、最初の画面で入れた名前が入る。入れなかったときは `User`。15 文字まで。同じ名前の行がいくつあってもよい |
| `is_public` | 整数 | 一覧に載せてよいなら 1。既定は 0 |

- `user_name` は、確定のときに入ります。
- `sock_id` と `message` には、仮の結果が入ります。分析ができるまでの代わりで、書かれた「と」とは関係なく決めた値です（作っているのは `back/src/drawings.py` の `make_result`。[api.md](api.md) の「仮の結果」）。仮の結果が入った行と、あとで分析の結果が入る行は、台帳の上では区別できません。
- `font`、`reading`、`is_public` は、分析と一覧の機能ができてから使います。いまは列だけ用意してあり、値は入れていません（`font` と `reading` は空、`is_public` は 0）。
- `user_name`、`sock_id`、`message` を入れるようになる前の行では、この 3 列は空です。

表は、最初の確定のときに自動で作られます（`back/src/db.py` の `SCHEMA`）。列を変えるときは、手元の `ito.sqlite3` を消してから作り直してください（作り直すと、手元の記録は消えます）。

`target` の列を足したときも、移行の仕組みは作っていません。手元の台帳は開発用なので、`target` の列がない古い `ito.sqlite3` が残っていたら、消して作り直してください（`docker compose exec backend rm data/ito.sqlite3`）。

### 書く順番と、失敗したとき

1. 仮の結果（くつしたとメッセージ）を作る。ここでは何も置かない。
2. 画像 2 枚と線のデータを、オブジェクト置き場に置く。
3. 台帳に 1 行書く。

1 で失敗したら（くつしたの台帳が読めないとき）、何も置かずに、API は 500 を返します。2 と 3 の途中で失敗したら、置いたオブジェクトを消して、API は 500 を返します。台帳に行があるのにオブジェクトがない、という状態は作りません。同時に確定が来たときは、台帳への書き込みを 1 つずつ順番に行います。

### 中身を見る

リポジトリの直下で実行します。まだ 1 回も確定していないと、フォルダや表がないのでエラーになります。

```bash
# 台帳の新しい 10 行
docker compose exec backend python -c "import sqlite3; [print(r) for r in sqlite3.connect('data/ito.sqlite3').execute('select id, created_at, user_name, sock_id, message, target, duration_ms, stroke_count, point_count, image_1024_key, image_256_key, strokes_key from drawings order by created_at desc limit 10')]"

# オブジェクトの一覧
docker compose exec backend ls -l data/objects/drawings

# 画像を PC に取り出して見る（<id> は台帳の id に置き換える）
docker compose cp backend:/app/data/objects/drawings/<id>_1024.png .
docker compose cp backend:/app/data/objects/drawings/<id>_256.png .

# 線のデータを展開して見る
docker compose exec backend python -c "import gzip; print(gzip.decompress(open('data/objects/drawings/<id>.json.gz', 'rb').read()).decode())"
```

## 本番での保存先の切り替え

バックエンドは Cloudflare のコンテナで動きます。コンテナからは R2 と D1 を直接使えないので、Worker に HTTP で頼みます。切り替えは環境変数 1 つです。

| 環境変数 `ITO_STORE_URL` | 保存先 |
|---|---|
| なし（手元） | フォルダ `back/data/objects/` と SQLite `back/data/ito.sqlite3` |
| あり（本番。例: `http://ito.store`） | Worker 経由で R2 と D1 |

バックエンドが Worker に頼む口は、次の 3 つです（仮。インフラ担当と合わせて決める）。どれも、成功なら 2xx を返します。

| メソッドとパス | 本文 | Worker がすること |
|---|---|---|
| `PUT <ITO_STORE_URL>/objects/<キー>` | ファイルの中身そのまま | R2 に、そのキーで置く |
| `DELETE <ITO_STORE_URL>/objects/<キー>` | なし | R2 から消す（無くても成功にする） |
| `POST <ITO_STORE_URL>/db/query` | `{"sql": "INSERT INTO … VALUES (?, ?, …)", "params": [値, …]}` | `sql` に `params` を順に当てはめて、D1 で実行する |

- キーは `drawings/<id>_1024.png` のような形で、手元と同じです。
- D1 の表は、`back/src/db.py` の `SCHEMA` で先に作っておきます（本番では、バックエンドは表を作りません）。
- 実装は `back/src/storage.py` と `back/src/db.py` にあります。実際の Worker とつないだ確認は、まだしていません。

## 決まっていないこと

- 本番で、コンテナの中の Python から D1 と R2 にどうつなぐか（インフラ担当と相談）。
- 手元のデータを PC 側のフォルダに残すか（`compose.yaml` の変更が要る）。
- 「と」の画像を誰でも見られる URL で配るか。
- 深層学習に渡す前に、余白を切る・中央に寄せるなどの加工をするか（分析の担当と相談。いまは枠の全体をそのまま保存している）。
- 記録をいつまで残すか。
- お題の字（`target`）と意図（`intent`）を ITO に入れるか。いまは `target` を「と」の固定にし、`intent` は保存していない。
- 画像を誰が描くか。いまはフロントが描いて送っている。サーバーが線のデータから描く方式にすると、`image` を送らなくて済む。
